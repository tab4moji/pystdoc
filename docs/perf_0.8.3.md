# 0.8.3 性能改善の記録

## 症状

`docgen` の第1フェーズ (`[1/5] Scanned` から `[2/5] Enumerated` まで)
が、シンボル数に対して二乗で遅くなり、その間は何も出力されない。

## 原因

1. `link_variables_to_functions`
   - 変数 × 関数の組ごとにファイル全体を読み直していた。
   - Java の gson (264 ファイル / 4,905 シンボル) で 562 万回の読み込み、
     301 秒。時間の大半は `splitlines` と `open`/`read` で、正規表現
     検索は約 4%。
2. `order_symbols_by_levels` のランク付け
   - 解決済みの SCC を除外せず、子が取り出されるたびに親を再投入していた。
   - 再投入は経路数に比例して増える。Lua (C, 2,367 シンボル) で
     `popleft` が 262 万回。
   - 処理順が文字列 set の走査順 (ハッシュシード) に依存するため、
     同じ入力で 1.7〜20 秒と揺れた。

言語別のパース (FQDN 生成) は 2〜6 秒程度で、支配的ではなかった。

## 修正

- ファイルを1回だけ読み、単語の逆引き表で参照を探す (`var_linker.py`)。
- 解決済みの SCC を再投入しない (`level_graph.py` の `rank_sccs`)。

## 検証

元実装と出力を比較し、すべて一致した。

| 項目 | 元実装 | 修正後 |
|---|---|---|
| link: gson 60 ファイル | 9.7s | 0.016s |
| link: moshi (Kotlin) 86 ファイル | 35.6s | 0.034s |
| link: lua (C) 30 ファイル | 31.9s | 0.049s |
| link: Python 60 ファイル | 34.1s | 0.038s |
| link: gson 全量 | 301s | 0.16s |
| order: lua 全量 | 3.9s (最大 20s) | 0.016s |

計測は 2 コアのサンドボックスで、絶対値は環境で変わる。比率は変わらない。
全量の link は、元実装との出力比較を部分集合でのみ行っている。
